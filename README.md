# GetGood — Practice Arena

![CI](https://github.com/yiqunqiao/Getgood/actions/workflows/ci.yml/badge.svg)

A local hackathon demo for practising evidence-backed review of AI-generated code.

## Start on macOS

Requires Python 3.10 or newer. Open this folder in VS Code, then open **Terminal → New Terminal**:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python run.py
```

Open **http://127.0.0.1:8000** in your browser. Keep the terminal running. Stop with **Control+C**.

Next time, run only:

```bash
source .venv/bin/activate
python run.py
```

Windows PowerShell: use `py -m venv .venv` and `.venv\Scripts\Activate.ps1`, then the same install/run commands. If port 8000 is occupied, stop the old process or run `python -m uvicorn backend.app:app --host 127.0.0.1 --port 8001` and open port 8001.

## Architecture

- `frontend/`: English HTML/CSS/JavaScript UI, served by FastAPI. No Node build step, CDN or external fonts.
- `backend/app.py`: API, server-recorded hint usage, local JSON progress.
- `backend/grader.py`: fresh temporary directory per target, pytest JUnit XML, 5-second timeout.
- `tasks/`: three exercises with shown code, reference code and three faulty variants each.
- `harness/conftest.py`: fresh fake database, gateway and wallet per test.
- `tests/`: integration checks for the three-act journey, guided-level rules, consequences, invalid code, boundaries and timeout.

The interface uses plain JavaScript so this local demo needs no frontend build. The PR Gatekeeper page is a prepared concept example: the senior enters a comment, confirms a risk tag, and sees the three matching exercises with their recorded progress. It does not read or write GitHub pull requests.

## Grading rules

- `Run on reference` checks the reference implementation only and does not update progress.
- `Compare without recording` runs the full evaluation without adding a submission or changing the current level. Because it shows detailed feedback, later submissions for that exercise count as practice rather than independent evidence. Hints already requested remain recorded.
- `Submit` first checks the reference. If it passes, the suite runs against V1, V2 and V3. This is mutation-style testing: a useful safeguard fails on targeted buggy variants and passes on legitimate reference behaviour. The variants are hand-written, not generated by a mutation tool.
- Only assertion failures count as caught variants. Syntax/collection errors, exceptions, skipped tests and timeouts do not count as evidence.
- A failed assertion on the reference means the test rejects correct behavior; this may be overblocking or a bad test expectation, not automatically an accurately diagnosed learner misconception.
- Judgement matching uses risk type and configured acceptable locations: the request_id parameter line or the external-effect line. The current UI supports one judgement per exercise because these exercises each have at most one known risk. Third exercise expects no risk found within the stated scope.
- Verified boundaries need the corresponding variants to be caught. Concurrent execution has no validator and cannot be marked verified.
- The fixed consequence choice is also graded deterministically; the first two tasks identify a duplicated external operation and the exception task permits a legitimate new request.
- Guided success stays at Needs guidance even if no hint is opened. An Independent or Exception submission earns independent credit only if it passes without hints, a loaded presentation example, or prior detailed feedback for that exercise. A successful assisted attempt is recorded as Guided practice, Demonstration completed, or Practice completed after feedback. Independent success in both coupon and refund-exception tasks reaches Verified across scenarios. A later failed recorded submission lowers the level by one.
- An honest unverified boundary does not erase evidence already established for sequential operations. Concurrency is shown separately from the latest recorded declaration: Not verified, Needs guidance, or Needs guidance with an unsupported verified claim.
- Levels are demo evidence labels, not a validated measurement of general engineering competence.

## Scope and limitations

This is a **single-learner local demo for trusted test input**, not a public code execution service. Submitted Python has the permissions of the Python process. Temporary directories, timeouts and a local session token do **not** provide sandbox isolation. Keep the server on `127.0.0.1`; do not expose it publicly or run untrusted submissions. Public deployment requires a genuinely isolated execution service, resource limits and authentication.

A source-code repository necessarily contains the reference implementations and demo examples; "hidden" means hidden from the normal task UI, not inaccessible to someone who owns the source. Presentation shortcuts intentionally reveal prepared answers. Loading either shortcut is recorded by the backend for that exercise, even if the learner edits the form or refreshes the page. The marker is cleared only when local progress is reset. No LLM API, user accounts, real GitHub integration, production payment gateway, concurrency verification, or empirical learning study is included. This local record tracks use of in-app assistance; it cannot detect answers copied from source code or outside the app, so it is not a certification of independent mastery. Records persist in `data/progress.json`, which is excluded from Git. The PR Gatekeeper preview uses one prepared PR, an entered senior comment, explicit tag confirmation and a fixed matching sequence with local progress. The comment is not posted anywhere.

Compared with the larger product document, this version uses a fixed consequence choice and omits free-text consequence explanations and explicit per-judgement test-name associations. It records evidence for the whole submission. Test targets execute sequentially (at most four 5-second executions), rather than in parallel, to keep local resource usage simple.

## Verify

```bash
python -m pytest tests -q
```

## Third-party APIs and dependencies

This local demo does not call a third-party API or an LLM. Runtime dependencies are FastAPI and Uvicorn; pytest runs submitted tests and httpx supports the integration tests. Versions are pinned in `requirements.txt`. No GitHub credentials are needed to run the demo. The CI workflow checks tests and Python syntax on pushes and pull requests.

## API

`GET /api/tasks`, `GET /api/progress`, `POST /api/demo/{task_id}/{kind}`, `POST /api/run`, `POST /api/compare`, `POST /api/submit`, `POST /api/hint/{task_id}`, `POST /api/reset`. POST requests require the session token from `GET /api/session` in `X-GetGood-Token`. The browser adds it automatically.

References: [FastAPI request bodies](https://fastapi.tiangolo.com/tutorial/body/), [pytest output and JUnit XML](https://docs.pytest.org/en/stable/how-to/output.html).
